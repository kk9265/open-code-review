# 按单号归集与 AI 审查队列

左侧“审查”默认进入[审查结果](http://127.0.0.1:5484/reviews)，查看已完成、失败等历史轮次，支持搜索和分页。“审查队列”位于 <http://127.0.0.1:5484/reviews/queue>，优先显示排队及运行中的任务，随后展示最近的执行记录，最多100条；任务详情 `/reviews/queue/runs/<id>` 用于查看目的、阶段、覆盖、查阅证据和冻结输入，并保留目的编辑与重试。草稿独立位于 `/reviews/drafts`。

审查结果采用左右布局：左侧以仓库、分支、需求单为父级目录，下面按时间从新到旧积累历史轮次，右侧只阅读问题、位置、严重程度和影响，备注与反馈直接展开。“审查过程”链接进入队列详情，修改目的、预期行为、执行统计、覆盖及原始输入均不在结果页展开。原引擎历史轮次根据结构化意见生成精简展示，不改写已保存的原始报告；新报告正文也不再插入目的或过程信息。部分报告保留简短状态提示，具体缺口进入过程页查看。目录显示当前归属提交数，各轮显示其冻结提交数；复审次数不会累加成提交总数。分组按50个分页，组内保留所有历史轮次，搜索支持标题、单号及仓库。左侧底部固定“未分类”，可搜索、分页和关联需求单。正文支持Markdown，渲染时禁用原始HTML和危险链接。

## 当前配置

- 跟踪 `zgame/master`、`zgame_china/dev/1.1.15.235.1`，每 300 秒同步。
- 模型连接：AI Mana；模型：`glm-5.3`（用户最新指定）；队列已启用，不限制每轮累计 Token 用量。
- Windows 自动读取 `%LOCALAPPDATA%/.aimana/proxy.json` 的当前代理端口。AI Mana 必须保持运行，无需复制其密钥。
- Linux 可使用手动 API 地址，当前执行器支持兼容 OpenAI Chat Completions 的服务。非本地服务从 `OCR_LLM_API_KEY` 读取凭据。

## 从提交到结果

1. 提交并推送到已跟踪的分支。只有跟踪起点之后发现的提交参与归集。
2. 提交日志中包含一个完整飞书链接，例如 `https://project.feishu.cn/zg/story/detail/7131560109`。也支持 `issue/detail/单号`。
3. 按仓库、分支、完整单号链接归组；不同项目空间或 story/issue 类型不会串单。没有链接、多个链接、合并提交进入“待归类”。
4. 同单号已有待执行任务时，后续提交加入该任务；开始时固定提交 SHA 列表和模型配置。
5. 全局只有一个运行中的任务。运行期间的新提交创建下一轮；每轮包含当前归属于该单的全部已发现提交，并附上上一轮完成结果作为参考。
6. 页面展示轮次、状态、完整提交差异输入及 AI 结果。当前列表最多显示最近 100 轮和 100 条提交，待归类优先。

## 人工操作

“备注与反馈”仅供用户填写，助手不将审查结论写入该输入框。本次误写入job10的助手补核内容已清空，原生报告和执行记录保留。

- 队列任务详情展示“第一阶段自动生成的修改目的”和“本轮采用的修改目的”。无需人工填写，系统会根据本轮聚合的提交说明/diff自动分析目的，然后进入review；这些信息不放入报告正文或结果页。
- 人工修订可选，用于补充预期行为或修正推断；保存后覆盖该需求单后续轮次采用的目的。未改动的自动稿不会固化为人工覆盖，留空恢复自动生成。“保存目的与备注”不调用AI，也不改变运行中或历史轮次；复审仍会生成初步分析，但实际目的优先采用人工修订。按原输入重试保留原目的/输入，不重复生成已有目的。
- 在结果详情的“备注与反馈”中补充业务背景或指出误报。“保存备注”仅保存，不调用 AI。
- 右上角“重新审查”与“提交反馈并重新审查”使用输入框当前内容，附上所选原轮次结果，以原提交列表创建独立复审轮次，使用当前模型配置。无须先保存；也可不填写反馈直接复审。
- 新轮次保存已提交反馈快照，并提供返回上一轮的链接。后续编辑备注不会改写已提交的反馈。重复提交旧页面会被拒绝，刷新后再操作。

- 展开“提交归属”，填写目标飞书链接，点击“调整归属并入队”。可以移到已有单号；旧的已固定轮次不会被改写，后续轮次采用新归属。
- 合并提交手动归类后，使用相对第一父提交的差异，需确认其中变更归属。
- “暂停队列”停止开始新任务，当前任务继续；“取消排队”仅取消尚未开始的轮次。
- 失败或中断可以“按原输入重试”，新建独立重试记录；模型、预算和提交列表沿用原记录。AI Mana 的传输端口重新发现。
- 修改模型或预算后，用右上角“重新审查”创建新轮次；原结果保留。
- 重启后待执行任务继续，原运行中任务标记为中断，避免不知情地重复调用模型。
- 仓库归档后，不开始它的新轮次。

## 审查范围与限制

当前 v13（`ticket-direct-v13`）已按用户要求移除工作台的原引擎接入。正式审查直接使用一段持续会话读取统一净补丁和必要源码；不再调用原引擎的分组、逐组循环、意见收集/过滤或额外的定向复核。Web 构建依赖中已不包含 `internal/agent`、`internal/llmloop`。历史引擎记录仅用于读取旧轮次，历史数据格式和原始结果不改写。

审查开头使用独立的系统规范，不再拼接旧引擎模板：源码可观察事实不等于缺陷；必须给出成立的触发、需求/接口契约依据和实质影响，不能把日志偏好、风格或未证实的需求当确认问题。提交意见前必须读完整相关控制流，逐项排除前置守卫、终态标记、锁、提前返回等反证；被已读反证阻断的路径应撤回，不能降为suspected继续保留。每条意见增加 `requirement_basis`、`countercheck` 和 `counterevidence` 引用，程序验证其存在和引用有效性，但是否支持结论仍由模型判断。完整已读源码始终保留在同一会话中，不再自动把旧正文裁成片段。

保留目的准备、冻结输入、只读工具、source_ref、依赖全树核对、批量部分成功保存、幂等、15分钟及80次新查阅预算。模型通过返回的检查id更新已有检查，可在该检查内用 `discard_findings` 明确撤回已被反证推翻的意见；程序检查归属并保留单调递增的意见编号。覆盖由明确保存的检查计算，不再由原引擎manifest代替；未覆盖不能正常结束，pending/gap即使已结束也保存为部分结果，同文件另有checked不能掩盖未闭合检查。新会话轨迹保存于 `.ocr-data/review-sessions/<jobID>/review.jsonl`，旧 `.ocr-data/native-sessions/` 保留供历史核对。

结果页明确区分模型的confirmed/suspected判断，并展示触发和影响；历史v12的suspected也恢复显示“存疑，尚未确认”及复核理由，未改写数据库内原报告。v13已部署Web/维护CLI，备份 `.local-go/before-direct-v13-20261016-202639`；哈希、页面、历史job行与外键核对通过，队列恢复原开启状态。单会话工具往返、完整源码保留、完成覆盖、意见撤回/防复活/编号、反证字段和历史存疑展示回归通过，构建/vet/英文/LF检查通过。全量测试仍有与v12基线同名的CLI用户目录/输出路由失败，没有新增失败名称。部署时未发起真实复审；随后按用户授权完成唯一一轮job17对照，结果如下。

历史 v12（`ticket-submission-v12`）将保存检查结论和候选意见合并为 `submit_review_checks`。新检查由程序编号，意见嵌套在对应检查中，位置从 `source_ref` 提取，不再提交 `path_id`。单目标工作项可省略目标；多目标必须从改动文件白名单明确选择，依赖源码只作为证据。依赖假设提交文件名、行为和依据，由程序按文件名及冻结 SHA 解析内部编号，仍须已有完整树缺失核对。

只有本轮最终 SHA 的成功源码读取发放 `source_ref`，返回路径及可引用行范围；搜索、差异、历史读取和失败调用只显示查询记录。缓存恢复先于总查阅预算检查，重复缓存不消耗新查阅额度。原“6 次查阅或连续 2 次未命中”仅提醒保存，工具轨迹自动持久化；未得出结论时可保存 `pending`，不计为完成覆盖，也不能提交意见。保留整轮 15 分钟、80 次新查阅和原请求预算。

每次提交逐项返回字段错误和合法候选；独立检查分别原子保存，失败项不留下半份检查或意见。相同成功提交可幂等重试，隐式目标参与幂等身份，避免不同工作项被误合并。保存回执和指标进入原有运行 JSON，无数据库迁移。过程页展示无校验错误提交数/总提交数、校验失败后的实际模型请求数、成功的纯保存提交数和检查点门槛拒绝数。这里的成功率按工具调用计算，幂等重试也计入调用；纠错指标计下一次实际发出的模型请求，不推断该请求内容是否在修正错误。

实际提速仍需相同输入、模型和预算的前后对照，比较上述指标以及整轮耗时、查阅数，同时检查未覆盖目标、证据有效性和未闭合缺口。开发时没有自动发起真实模型复审；后续经用户授权的单轮验证如下，v11 及更早说明保留为历史。
